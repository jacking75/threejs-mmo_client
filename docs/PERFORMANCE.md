# 성능·실패 상황 실험

## 재현 방법

`npm ci` 후 다른 개발 서버를 종료하고 `npm run test:perf`를 실행한다.
설치된 Chrome, 로컬 테스트 서버, 단일 Playwright worker를 사용한다.
원시 보고서는 Git에서 제외한 `docs_working/performance-results.json`, 화면은 `test-results/`에 남는다.
공개 기준 데이터는 [client-baseline.json](measurements/client-baseline.json)에 정리한다.

측정 환경: Windows, Node 24.19.0, Intel Core i7-13700H, Intel Iris Xe / NVIDIA RTX 4060 Laptop GPU가 있는 PC의 Chrome headless.
실제 Chrome이 선택한 GPU·절전 상태와 화면 주사율에 따라 값이 달라진다. 이 결과를 저사양 기기의 성능 보증으로 사용하지 않는다.
낮은 해상도/DPR 및 그림자 해제 비교는 비용 실험이며 별도 저사양 하드웨어 실측은 아니다.

## 측정 항목

- 게임 인벤토리에서 검·의상 100회 교체, 로비↔필드 100회 전환.
- Three.js renderer.info의 geometry/texture 수, 씬의 고유 material 수, draw call/triangle 수.
- Chrome CDP 강제 GC 후 JS heap 사용량 전후. JS heap과 GPU 메모리는 다른 값이다.
- 1280×720 DPR1 그림자 off/on, 1920×1080 DPR2 그림자 on: 30프레임 준비 후 60개 rAF 간격의 중앙값·p95.
- GLB 요청 차단 후 절차형 fallback, 900×650 resize, blur 입력 초기화, 탭 frozen→active 복귀.
- 부하 객체 0/50/200 × 관심 반경 200/15 × 수신 20/5Hz의 수신 본문 KiB/s와 화면 프레임 시간.
- 편도 지연 50/150/300ms × 예측 on/off에서 키 입력부터 첫 0.05m 화면 변화까지 걸린 시간.

`frameMs`는 rAF 간격이며 CPU/GPU만의 순수 렌더 시간은 아니다. 낮은 값 하나를 FPS 보증으로 해석하지 않는다.
수신 바이트는 JSON 본문이며 TCP/HTTP 헤더와 송신 입력은 제외한다. 부하 객체는 정적인 모형이다.
실제 전투·움직이는 수백 캐릭터·서버 동시접속 부하를 대신하지 않는다.

## 합격 조건

같은 장비로 되돌아왔을 때 geometry/material 수가 같고, 각 필드 폐기 후 GPU geometry가 3개 이하이며 누적 증가하지 않아야 한다.
JS heap 전후 수치는 참고치로 별도 기록하고, 증가량만으로 누수 여부를 단정하지 않는다.
네트워크 실험 내내 연결이 유지되고 각 입력 반응이 2초 이내여야 한다.
도메인 테스트는 30/60/120fps에서 2초 이동 거리와 0.72초 공격 종료 시점을 한 프레임 오차 안에서 검증한다.

## 발견한 문제와 수정

초기 네트워크 실험은 서버의 50ms setInterval 지연이 누적되어 미확인 입력이 100개까지 늘고 연결이 끊겼다.
화면을 기록만 하던 측정 테스트에도 연결 유지 조건을 추가했다.
서버는 실제 경과 시간을 누적해 50ms 고정 tick을 처리하며 한 번에 최대 250ms까지만 따라잡는다.
클라이언트와 서버의 이동 단위는 같고, 임의 dt나 속도를 클라이언트로부터 받지 않는다.
수정 전 실패 데이터는 `docs_working`의 진행 기록에 남기고 공개 기준 데이터는 수정 후 측정으로 갱신한다.

## 2026-11-03 수정 후 기준 결과

| 반복 조건 | 시작 | 종료 |
| --- | --- | --- |
| GPU geometry | 677 | 677 |
| texture | 1 | 1 |
| 고유 material | 511 | 511 |
| draw call / triangle | 447 / 22,552 | 447 / 22,552 |
| 강제 GC 후 JS heap | 17,401,396 bytes | 22,152,500 bytes |

100회 장비 교체와 100회 화면 전환 뒤 GPU/씬 자원 수는 같은 값으로 복귀했고, 각 필드 폐기 직후 GPU geometry 최댓값은 0이었다.
JS heap은 약 4.53MiB 증가했다. JIT·브라우저/테스트 캐시와 잔존 객체를 분리하지 않았으므로 **전체 메모리 누수가 없다고 판정하지 않는다**.
이 보고서는 GPU 해제 회귀 검사와 JS heap 기준값을 제공한다. 장기 실행 메모리 최적화를 할 때 heap snapshot 비교의 시작점으로 사용한다.

| 해상도 / DPR / 그림자 | rAF 중앙값 | p95 |
| --- | --- | --- |
| 1280×720 / 1 / off | 18.7ms | 19.2ms |
| 1280×720 / 1 / on | 18.8ms | 19.3ms |
| 1920×1080 / 2 / on | 18.6ms | 19.2ms |

이 환경은 rAF 제한 근처여서 설정별 차이가 작았다. 이 결과만으로 고해상도 그림자의 비용이 없다고 결론 내리지 않는다.
그림자 off 시 geometry 447/texture 0, on 시 geometry 677/texture 1로 자원 차이는 확인됐다.

| 부하 200개 조건 | 표시 객체 | JSON 수신 | 프레임 표시 |
| --- | --- | --- | --- |
| 반경 200m, 20Hz | 201 | 180.2 KiB/s | 18.5ms |
| 반경 200m, 5Hz | 201 | 63.4 KiB/s | 18.5ms |
| 반경 15m, 20Hz | 13 | 14.5 KiB/s | 18.7ms |
| 반경 15m, 5Hz | 13 | 4.6 KiB/s | 18.7ms |

영역 제한은 이 위치에서 수신 본문 크기와 표시 객체를 크게 줄였다. 프레임 시간은 단일 표본이라 향상을 주장하지 않는다.

| 편도 지연 | 예측 on 입력 반응 | 예측 off 입력 반응 |
| --- | --- | --- |
| 50ms | 25.4ms | 399.6ms |
| 150ms | 28.5ms | 596.6ms |
| 300ms | 29.6ms | 899.6ms |

이 비교는 앞 실험의 5Hz 수신·관심 반경 15m·부하 200개 설정에서 수행했다. 예측 off는 왕복 지연뿐 아니라
폴링 주기와 보간 지연을 포함한다. 순수 네트워크 RTT 측정이 아니다. 수정 후 모든 구간에서 연결을 유지했고
미확인 입력은 수신/지연 설정에 따른 범위에 머물렀다. 단위 테스트의 오류 주입 시 최종 이동·ack도 수렴했다.

네트워크 표와 원시 데이터는 전송/수신을 rAF에서 25ms 타이머로 분리한 뒤 다시 측정했다.
Hz 선택은 목표 폴링 주기이며 타이머 지연·응답 대기에 따라 실제 수신 빈도는 낮아질 수 있다.
